# 1. Network Components

A typical enterprise network contains multiple interconnected components.

### Key Components

| Component                | Purpose                         | Security Importance                                            |
| ------------------------ | ------------------------------- | -------------------------------------------------------------- |
| Workstations / Endpoints | Employee systems                | Common initial attack vector                                   |
| File / Database Servers  | Store sensitive business data   | High-value targets                                             |
| Application Servers      | Web, email, VPN services        | Externally exposed attack surface                              |
| Active Directory         | Identity and access management  | Target for privilege escalation and lateral movement           |
| Routers / Switches       | Network connectivity            | Can enable traffic interception or manipulation if compromised |
| Firewalls                | Filter network traffic          | First line of perimeter defense                                |
| DMZ                      | Isolates public-facing services | Limits exposure of internal systems                            |
| VPN Gateway              | Remote access                   | Common target for credential attacks                           |

# 2. Network Visibility

Network visibility allows analysts to understand what is happening across the environment.

## Host-Centric Logs

Generated by individual systems.

Examples:

* Windows Event Logs
* Linux syslog
* Application logs
* Antivirus logs
* EDR logs

Useful for investigating:

* Process execution
* User logins
* File access
* Service changes
* Malware execution

## Network-Centric Logs

Generated by network devices and security controls.

Examples:

* Firewall logs
* IDS/IPS logs
* Router/switch flow data
* Proxy logs
* VPN logs

Useful for identifying:

* Port scans
* Brute-force attacks
* Lateral movement
* C2 communication
* Data exfiltration

### Key Concept

```text
Host Logs
   ↓
What happened on the machine?

Network Logs
   ↓
Who communicated with whom?

Correlation
   ↓
Complete attack timeline
```

# 3. Network Perimeter

The network perimeter separates the trusted internal network from the untrusted Internet.

Common perimeter components:

* Firewalls
* Routers / Gateways
* DMZ
* VPN gateways
* Access-control systems

The perimeter is important because attackers commonly begin by probing externally exposed services.

### Common Threats

* Port scanning
* Exploitation of exposed services
* Brute-force attacks
* Unauthorized access
* Malware infiltration
* Data exfiltration

# 4. Monitoring the Perimeter

The lab demonstrated several attack scenarios.

Example firewall activity:

```text

BLOCK TCP attacker_ip:50003 -> internal_ip:23

BLOCK TCP attacker_ip:50005 -> internal_ip:53
```

### Observation

The same external IP attempted connections to multiple ports on a target in a short period.

### Interpretation

This pattern is consistent with **port scanning / reconnaissance**.

# 6. VPN Brute Force

VPN authentication logs contained repeated failed authentication attempts.

I analyzed the failed attempts using command-line filtering.

```bash
cat vpn_auth.log | grep FAIL
```

To group attempts by source IP:

```bash
cat vpn_auth.log | grep FAIL | cut -d' ' -f3 | sort -nr | uniq -c
```

### Observation

One source IP generated a significantly larger number of failed authentication attempts than the others.

The activity was followed by successful authentication events.

### Interpretation

This indicated a **VPN brute-force / credential attack** followed by successful access.

# 7. Reconnaissance Investigation

I started the incident investigation by examining blocked firewall requests.

```bash
cat firewall.log | grep "BLOCK" | head
```

I then counted blocked requests by source IP:

```bash
cat firewall.log | grep "BLOCK" | cut -d' ' -f5 | cut -d: -f1 | sort -nr | uniq -c
```

### Finding

The results showed one external IP responsible for the majority of blocked connection attempts.

The source attempted to reach multiple services including:

```text
21  FTP
22  SSH
23  Telnet
445 SMB
3389 RDP
```

### Interpretation

The repeated attempts against multiple ports indicated reconnaissance activity against the internal network.

---

# 8. Initial Access

After identifying the suspicious external IP, I searched the firewall logs for allowed traffic from the same source.

```bash
cat firewall.log | grep <SUSPICIOUS_IP> | grep "ALLOW"
```

The results showed that some connections from the suspicious source were allowed.

I then pivoted to the VPN logs.

```bash
cat vpn_auth.log | grep <SUSPICIOUS_IP>
```

The investigation showed:

```text
Multiple FAILED authentication attempts
              ↓
Successful authentication
              ↓
Internal VPN IP assigned
```

### Finding

The attacker successfully obtained access to the internal network through the VPN.

---

# 9. Lateral Movement

After obtaining an internal IP address, I searched the firewall logs for traffic originating from the compromised host.

```bash
cat firewall.log | grep <COMPROMISED_IP> | grep "ALLOW" | head
```

The compromised host was observed communicating with internal systems over:

```text
22   SSH
445  SMB
3389 RDP
```

The targeted internal systems included:

```text
10.0.0.20
10.0.0.51
10.0.0.60
```

I then correlated the activity with IDS alerts:

```bash
cat ids_alerts.log | grep <COMPROMISED_IP> | head
```

Relevant alerts included:

```text
Possible SSH Scan
Possible MS-SMB Lateral Movement
Possible RDP Brute Force
```

### SMB Investigation

I filtered specifically for SMB-related alerts:

```bash
cat ids_alerts.log | grep -n <COMPROMISED_IP> | grep 'SMB'
```

The alerts showed repeated:

```text
Possible MS-SMB Lateral Movement
```

### Interpretation

The compromised host was attempting to move laterally through the internal network.

# 10. Command & Control (C2)

I searched the IDS logs for C2-related alerts:

```bash
cat ids_alerts.log | grep C2 | head
```

The logs showed periodic communication consistent with C2 beaconing.

Example pattern:

```text
01:00
07:00
13:00
19:00
```

The regular timing was an important indicator.

### Interpretation

Repeated connections at predictable intervals can indicate **malware beaconing to a C2 server**.

I then pivoted on the compromised host to identify additional alerts.

```bash
cat ids_alerts.log | grep <COMPROMISED_IP>
```

The investigation showed:

```text
C2 Beaconing
Suspicious HTTP
SQL Injection alerts
Possible scans
```

### Key Finding

An external IP was identified as the destination associated with the C2 communication.

# 11. Data Exfiltration

After identifying C2 activity, I investigated outbound traffic from the compromised host.

```bash
cat firewall.log | grep <COMPROMISED_IP> | cut -d' ' -f5,6,7 | uniq | sort
```

The host was observed sending repeated traffic to external destinations over:

```text
80
8080
```

I then correlated the activity with IDS alerts.

```bash
cat ids_alerts.log | grep <COMPROMISED_IP> | tail
```

Relevant alerts included:

```text
Possible HTTP POST Large Upload
Classification: Potential Data Exfiltration
```

### Interpretation

The repeated large HTTP POST uploads provided evidence of potential data exfiltration from the compromised host.

# 14. Investigation Techniques

### Filtering

```bash
grep "BLOCK" firewall.log
```

Used to isolate blocked firewall traffic.

### Counting Sources

```bash
cat firewall.log | grep "BLOCK" | cut -d' ' -f5 | cut -d: -f1 | sort -nr | uniq -c
```

Used to identify sources generating large numbers of blocked requests.

### Investigating Failed Authentication

```bash
cat vpn_auth.log | grep FAIL
```

Used to identify failed VPN login attempts.

### Pivoting

```bash
cat firewall.log | grep <IP>
cat vpn_auth.log | grep <IP>
cat ids_alerts.log | grep <IP>
```

Used to correlate activity across different log sources.

### Searching for C2

```bash
cat ids_alerts.log | grep C2
```

### Searching for SMB Activity

```bash
cat ids_alerts.log | grep <IP> | grep SMB
```

# 16. 🧠 What I Learned

* Network security depends heavily on **visibility and log collection**.
* Firewall logs can reveal reconnaissance and suspicious perimeter activity.
* Repeated connections to many ports can indicate port scanning.
* Repeated authentication failures from one source can indicate brute force.
* A successful login after many failures can be an important pivot point.
* Compromised hosts can be identified by correlating VPN, firewall, and IDS logs.
* SMB, SSH, and RDP traffic can provide evidence of lateral movement.
* Regular network connections can indicate C2 beaconing.
* Large outbound HTTP POST requests can indicate potential data exfiltration.
* Correlating multiple log sources provides a much stronger picture than analyzing one log independently.
* Splunk can make large-scale log analysis significantly more efficient.

---

# 17. ⚠️ Important Takeaways

The most important skill from this room was **log correlation**.

A single event may look harmless, but connecting events across different sources can reveal the complete attack chain:

```text
Firewall
   +
VPN
   +
IDS
   ↓
Attack Timeline
```

The investigation should therefore follow a **pivot-based approach**:

```text
Suspicious IP
     ↓
Search across all logs
     ↓
Find related events
     ↓
Identify compromised host
     ↓
Search for internal activity
     ↓
Look for C2 / exfiltration
```
